# 语音恢复改动设计

状态：原始设计稿，2026-11-03；2026-11-04 已实施离线实验链路，当前范围见 [使用说明](voice-recovery.md) 与 [实现记录](voice-recovery-progress.md)。下文保留原方案，尚未完成客户端播放或手机验收。

## 1. 目标与原则

把保留方 B 的单聊恢复到 A 的视角：B 发出的语音在 A 端为收到，A 发出的语音在 A 端仍为本人发送。原音频、真实服务器消息 ID、时间及其他消息内容保留；仅转换身份、方向和目标数据库必需的本地关联。

“角色互换”指同一真实发送者在两个账号下的收发视角转换，不交换真实账号身份，不把 B 的发言改成 A 的发言。目标是微信中可以点击播放的原语音，不以文字转写或独立音频文件代替恢复。无须引入 Whisper 或转写模型，无须重新编码音频。

首轮沿用 macOS Apple Silicon / 微信 4.1.13 / 单个 message_0.db 的范围。语音适配先限定已核验的 media_0.db 结构；发现额外媒体分片时，语音模式明确停止，后续另行适配。其他消息类型的支持范围不随本设计扩大。

## 2. 当前依据与待确认项

已检查当前源码：

- workflow.py 的 SUPPORTED 不含语音类型 34；save_chat 和 prepare_plain_restore 都会拒绝语音。
- RELS 固定为消息、资源、会话三库；operations.ALL 再加入联系人库。媒体库没有进入正式导出、候选、应用或撤回流程。
- 取钥器会发现 *.db，但 CLI 的完成条件和完成后验证只有四个基础库，因此已有取钥成功不能证明媒体库密钥可用。
- tools/wechat-local/media_pipeline.py 已有按会话 username 和真实 server_id 查询 VoiceInfo.voice_data 的读取实现，可复用查询思路；它不是跨账号语音写入的验证。
- sync.py 在 added=0 时跳过应用。新增语音支持后，这会漏掉“消息已在、音频缺失”的修复。

本次仅对已有离线明文副本读取表结构和聚合统计，未读取语音内容，未启动微信或访问真实运行库。观察到的结构为：

```sql
CREATE TABLE VoiceInfo(
  chat_name_id INTEGER, create_time INTEGER, local_id INTEGER,
  svr_id INTEGER, voice_data BLOB, data_index TEXT DEFAULT '0'
);
CREATE INDEX VoiceInfo_INDEX ON VoiceInfo(chat_name_id, svr_id);
CREATE UNIQUE INDEX VoiceInfo_UNIQUE_INDEX
  ON VoiceInfo(chat_name_id, create_time, local_id, data_index);
CREATE TABLE Name2Id(user_name TEXT PRIMARY KEY);
```

这证明语音数据及本地索引需要单独处理；现有副本中也存在空音频行，不能将“存在 VoiceInfo 行”视为音频完整。

实现前须通过授权样本或离线对照确认：VoiceInfo.local_id 与消息 local_id 的关系、data_index 的含义、同一语音多行的语义，以及语音 packed_info_data / 消息正文 / 资源元数据是否含其他账号或本地索引。未知字段先保留字节，但必须验证它们能否跨账号保留；不凭字段名重写、不在语义不明时应用。现有 flip_packed 只适配已观察到的方向结构，需要先验证真实语音是否符合该结构。

## 3. 数据转换规则

| 数据 | 处理 |
| --- | --- |
| 真实发送者 username | 保留；以其是否等于目标账号判断发出/收到 |
| server_id / VoiceInfo.svr_id | 保留源真实值；发生内容或身份冲突即停止 |
| 原始 voice_data | 逐字节复制，以 SHA-256 校验；不转码 |
| 时间、时长、正文及其他载荷 | 默认原样保留；时长字段须先确认来源和单位 |
| 消息 real_sender_id、packed 方向字段 | 映射到目标账号；复用现有转换逻辑前验证语音结构 |
| 媒体库 chat_name_id | 用媒体库自身 Name2Id 映射到目标端另一方 username；不能复用消息库数值 ID |
| 消息 local_id | 由目标消息表分配，建立 server_id → 目标 local_id 对照 |
| VoiceInfo.local_id / data_index | 先核实语义；仅在证据表明是本地关联时转换，其他内容保留 |
| 资源库中的会话、发送者及消息关联 | 使用各自目标映射；保留已验证可跨账号的其他字段 |
| 会话摘要 | 沿用保护较新摘要和草稿的规则；最新消息为语音时验证摘要、方向与类型 |
| 消息 status、下载/播放等状态 | 不直接套用文本的 status=3；核实历史语音的有效状态，仅改动经验证必要的字段 |

源记录筛选必须同时绑定所属账号、所选会话 username 和真实 server_id，不能只按 server_id 搜索并拼接其他会话数据。首次适配只接受一条明确匹配、非空且通过格式检查的音频行；多条匹配先拒绝，不擅自挑一条或拼接。目标端的同会话孤立缓存也要参与冲突检查。

## 4. 改动位置

| workflow.py | 支持经能力检查通过的类型 34；导出带音频的 bundle；恢复消息后补齐媒体和资源关联；返回语音明细统计 |
| operations.py | 将固定文件集合扩展为受校验的任务文件集合，覆盖媒体快照、导出、候选、应用前检查和回撤 |
| cipher.py | 复用逐库密钥、原盐加密和隐式 rowid 保留；加入媒体库往返验证，必要时适配，不另做音频加密算法 |
| __main__.py | 增加显式语音能力选项；媒体库逐库验证及取钥完成条件同步扩展；现有密钥已覆盖时直接验证复用 |
| sync.py | 双侧从应用前快照取语音；音频修复也构成有效变化；预检、应用、部分失败和撤回均覆盖媒体库 |
| desktop_backend.py | 区分语音可恢复、缺音频、结构不支持、冲突，不再只用消息类型判断可恢复性 |
| desktop/ChatRescue.swift | 沿用五步向导，在预览中补充语音及阻碍数量，在验收页增加点击播放检查 |
| tests 与现有 SOP / CLI / 支持边界 | 合成回归、故障注入及分阶段验收同步更新；实机验收前不修改为“语音已支持” |

实现可采用 `--include-voice` 作为能力开关；该参数已在 0.4.0 本地开发版实现。基础文本流程继续只要求四库；启用语音后需明确验证源、目标媒体库的结构和密钥，不能四库取钥完成后提前结束。目标无 media_0.db 时首轮停止，不复制源账号的整库，也不自行创建未知密钥的新媒体库。

## 5. Bundle 与计划格式

引入 bundle v2：保留现有消息内容字段，新增逐条语音清单和独立原始音频文件。每条清单包含真实 server_id、绝对发送者身份、源语音行必要元数据、音频相对路径、字节数及 SHA-256；身份/元数据仅保存在私人 bundle，不写入公开日志。只携带授权单聊所需音频，不交付整个 media_0.db。

音频使用工具生成的名称，例如 `voice/000001.silk`。读取端限制路径位于 bundle 内，拒绝绝对路径、路径穿越、符号链接、重复条目及不合理体积；验证消息与音频一一对应及清单哈希。哈希用于检查完整性，不代替双方对资料来源和身份的确认。原音频格式不受支持或缺失时标记阻碍，不以已有转写冒充音频。

新代码继续读取 v1 bundle，并按原范围处理；语音 bundle、含媒体库的导出报告、单向计划及双向计划使用新版本和明确 capability 标志，使旧版本拒绝读取。旧版本不能忽略音频后照常应用。

任务计划区分 `read_set`（快照与一致性依赖）和 `write_set`（实际替换的库）。路径只允许现有基础库和经适配的 `message/media_0.db`，每个库展开 DB/WAL/SHM，并记录不存在的 sidecar。重新枚举数据库清单，拒绝计划后新增媒体分片等变化。apply 不得相信计划内任意相对路径来扩大写入范围。

## 6. 去重和缺音频处理

| 目标状态 | 决策 |
| --- | --- |
| 消息缺失，源音频完整 | 新增消息、必要资源关联和音频 |
| 消息一致且音频已完整一致 | 跳过；重复执行不修改库 |
| 消息一致但音频缺失/为空，源音频完整 | 只补缺失音频及已确认必需的状态/关联；不重复插入消息 |
| 同一消息双方均缺音频 | 阻碍该次完整语音恢复，不生成可应用计划 |
| 源缺音频，但目标已有完整音频 | 保留目标音频；双向计划可用该侧原始快照作为另一侧音频来源，必须绑定同一真实消息及身份 |
| 同一消息对应不同非空音频或元数据冲突 | 停止，保留双方原件，不覆盖或自动选择 |
| 多行匹配或不明本地索引 | 首轮停止，待结构适配 |

首轮不静默跳过失败语音，也不以空语音气泡表示成功。双向场景先从两侧不可变快照形成消息与音频对照，再分别生成候选；不以本轮刚写入另一侧的数据库作为新来源。

报告新增 `voice_added`、`voice_repaired`、`voice_skipped`、`voice_blocked` 和 `changed_databases`。是否应用由实际 write_set / 变化决定，不能继续只看 added。预览使用“新增语音 X 条，已有消息补齐音频 Y 条，缺失/冲突 Z 条”等用户可理解的文字。

## 7. 应用与回撤

保持“先生成可核对候选，再应用”的流程。任何媒体变化都必须进入与消息、资源、会话库同一份计划：

1. 微信退出后备份一致快照，复制前后校验所有依赖库及 sidecar；媒体结构及逐库密钥验证通过后再导出。
2. 在副本内生成候选；除完整性检查外，验证消息—身份—音频关联、原音频哈希，以及其他会话和原有音频未改变。
3. 用目标账号相应库的密钥和原盐重新加密，解密读回校验；不能把 B 的加密媒体库直接放入 A。
4. 应用前再次验证所有依赖和候选，协调保存原件，再替换 write_set。任意替换失败时对已触及库连同其 DB/WAL/SHM 回撤。
5. 对多文件替换不宣称文件系统整体原子性；先持久化操作日志，记录每个库的意图与完成状态，并同步文件及目录。进程中断后按日志和哈希判定，不能自动重跑、启动微信或声称已回撤。
6. 双账号仍分别记录成功、失败和部分完成，不能把一侧完成说成双方完成。撤回要覆盖媒体文件；任何依赖已产生新变化时拒绝用旧快照覆盖。

现有 plan/apply/undo 中所有依赖 RELS、ALL、state() 的路径都应统一迁移，避免候选含媒体库但撤回漏掉它。

## 8. 实施顺序与验收门槛

| 阶段 | 工作与完成条件 |
| --- | --- |
| P0 结构确认 | 使用已有授权离线资料确认双方方向、本地 ID、状态、data_index 和资源关系；形成脱敏结构说明及合成样本。不修改真实库 |
| P1 离线实现 | 完成 voice 模块、v2 bundle、媒体导出和目标候选；音频逐字节一致，身份/关联检查通过 |
| P2 完整恢复链 | 接入取钥完成条件、动态文件集合、CLI、双向补齐、故障回撤、撤回和五步界面；基础类型回归通过 |
| P3 电脑实机验收 | 用已生成并获确认的具体计划验证本人发出/对方发来两种方向、时长、完整播放、重启后再次播放、已有记录无损。不得要求用户删除真实记录来制造样本 |
| P4 手机单独验收 | 由本人使用微信官方迁移入口，逐条检查方向、时间、时长和播放；未完成时仅记录电脑结果 |

必要合成检查：不同库的稀疏 Name2Id rowid；目标 local_id 不同；其他会话同 server_id；空/损坏/多行音频；同消息不同音频；目标媒体库缺失；源/目标音频互补；消息全重复但有音频修复；两次恢复第二次无变化；较新会话与草稿保留；音频文件篡改及越界路径；缺媒体密钥与取钥过早结束；媒体 WAL 变化/新分片出现；写入各库失败及进程中断；双向部分完成；媒体变化后拒绝撤回；v1 兼容与旧版本拒绝 v2。

音频头检查只说明格式候选，SQLite 完整性只说明数据库结构；均不能证明微信播放或手机迁移。发布“支持语音恢复”的结论以相应实机验收记录为依据。
