# 多消息分片问题定位（2026-11-04）

本记录依据基线 `1215d16` 源码和临时合成数据库，不涉及真实账号、取钥或客户端验收。用户已批准完整方案，修复实现在 `codex/multi-message-shards` 工作区；实际验证记录见 `docs/testing.md`。

## 已复现的根因

使用 `tests/test_workflow.py` 的合成 fixture，额外复制出 `message/message_1.db`：

- `workflow.save_chat` 抛出 `v0.1 supports one message_0.db shard only`。
- `operations.state` 的结果没有 `message/message_1.db`；因此也没有该分片的 WAL/SHM。
- 将会话仅放在 `message_1.db`，保留空的 `message_0.db`，`sync.conversation_count` 返回 0。

上述复现使用 Python 3.14.6，临时数据库在退出时清理。

## 影响范围

- `workflow.py`：`_single_shard` 显式拒绝多分片；`save_chat` 和 `prepare_plain_restore` 固定读取/写入 `RELS[0]`。
- `operations.py`：`ALL`/`RELS` 固定，影响快照、导出、哈希绑定、候选加密、应用及异常回撤。
- `__main__.py`：密钥验证和 Mac 取钥完成分组仅包含固定四库。
- `windows_capture.py`：取钥前拒绝多分片，覆盖验证及回执数量固定。
- `sync.py`：会话计数仅查询第零分片，候选与应用前检查沿用固定文件集合。
- `desktop_backend.py`：会话枚举仅查询第零分片。
- `windows_backend.py`：文件锁和取钥回执覆盖判断使用固定四库。

不能仅删除 `_single_shard`：这会使其他分片的消息、编号冲突、密钥覆盖和原件变化被忽略。

## 已确认的完整修复范围

1. 统一枚举现有编号消息分片，按数字排序，严格验证路径；资源库、会话库、联系人库仍须完整存在。
2. 密钥验证和导出覆盖每个发现的分片；报告绑定精确文件集合及各库和 WAL/SHM 哈希。缺任意密钥立即拒绝，不跳过分片。
3. 单聊导出逐分片使用各自的 `Name2Id` 解析发送者，保留真实 `server_id`，检查跨分片的重复和冲突及表结构兼容性。
4. 恢复前跨目标所有分片查询编号与身份，按实际所在分片解析映射；不把不同分片相同本地编号当作相同身份。
5. 保留已有分片布局，不自动创建新分片。新增消息写入规则、资源本地编号和会话最后消息引用须明确并由合成用例验证；无法证明兼容的结构拒绝生成候选。
6. 候选、应用、回撤、双向同步及撤回使用精确的动态文件集合，拒绝计划后新增/删除分片或 sidecar、路径穿越、候选篡改。
7. CLI 与桌面会话列表汇总所有分片；更新公开文档中的单分片限制及报告行为。

替代范围是仅支持多分片源账号导出；该方案不能解决多分片目标账号的恢复限制。

## 必须验证的场景

- 会话仅在非零分片、同一会话跨多个分片、非连续编号与数字排序。
- 各分片同一本地 sender rowid 对应不同账号、local_id 重复，方向仍正确。
- 跨分片去重、正文/身份冲突、其他会话编号碰撞；不伪造编号或覆盖记录。
- 缺密钥或结构不兼容时拒绝，不产生可应用计划。
- 导出绑定篡改、计划后增加/删除分片或改变 WAL/SHM 时拒绝。
- 多分片加密导出、候选重新解密比对、应用中途失败时整组 DB/WAL/SHM 回撤。
- 单分片旧 bundle 和既有安全检查不回归。

合成测试不能证明微信客户端读取、真实 GUI 恢复或手机迁移成功，这些仍需独立人工验收。
