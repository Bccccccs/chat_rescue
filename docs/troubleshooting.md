# 失败处理与回撤原则

## 点击读取却提示旧回执不覆盖当前库

旧开发包可能在重新验证前拿旧回执库数量与当前清单比较，导致点击读取仍被要求重新读取。账号重新核验修复包会保留旧回执，直接验证当前每个必要库的配套钥、HMAC、完整性与本人身份，通过后写新回执。

若提示具体分片缺钥，请在出错账号卡片点“打开微信并登录账号”，本人登录所选账号，确认来源所需聊天完整后点击读取；运行中会获取缺少的当前密钥。另一账号已通过的结果保留。旧回执属于其他内部身份时仍拒绝，不能通过改owner或库数量解决。


## 带盐候选已解析，但HMAC检查0次

若诊断中`feature_locations`、`salted_key_literals`大于0而`hmac_checks`为0，旧整合包可能在嵌入盐值筛选阶段跳过了全部实际HMAC。读取修复包改为先验证盐值匹配项，再用实际首页验证其他已解析候选，仍要求所有必要库通过。

新版若提示`no-selected-salt-match`，表示候选附带盐值均未对应所选库，逐库HMAC也未通过；先由本人核对当前登录的来源/目标账号和“账号详情”的实际目录。不能仅凭此断言版本不支持或数据库损坏，也不能自动挑其他目录。诊断只保存计数和规范相对库名，不包含密钥、盐或内存地址。

原始密钥/显式盐值格式依据[SQLCipher官方API](https://www.zetetic.net/sqlcipher/sqlcipher-api/)；程序不修改库盐值、不关闭HMAC，也不尝试无凭据解密。


## 2026-11-09 整合开发版读取提示

- 主进程 0 个与多个分开提示；0 个可能是未启动或所选程序路径不同，不能误认为有多个微信。多个时显示数量与 PID，不自动结束任何进程。
- 普通目录选择会按当前工作区内的内部身份与目录查找密钥材料，重新执行全库 HMAC/完整性和本人昵称验证；不需要先载入旧角色选择。`account-material.json` 仅维护每账号的材料路径，不含密钥值或永久来源/目标角色。
- `SQLCipher query failed (code 26)` 现在附具体数据库相对名；密钥/目录不匹配或库状态异常需定位，不能用旧昵称或部分钥冒充已验证。不要删除数据库、WAL/SHM 或改报告。
- 已明确的 WCDB 三种 `.material` 备份不再误拦截；未知附属文件仍提示具体名称并保留现场。


发生异常时先停止当前步骤，保留原件、报告和候选，确认所有微信进程退出。不要为了重试删除手机、电脑上的原始记录，也不要通过编辑编号、关闭校验或强行覆盖来推进。

## 环境与权限

- `doctor` 提示 Python 或 SQLCipher 缺失：按 README 安装，再在仓库根目录运行检查。
- 找不到原版微信：在 Finder 确认实际应用路径，修改 `--app` 和 `--original-app`。
- 副本创建失败或输出已存在：保留已有目录，创建新的私人工作目录；不要覆盖原版。
- LLDB、调试或文件访问被拒绝：检查 Xcode Command Line Tools、专用副本的完全磁盘访问权限，以及终端的开发者工具/完全磁盘权限。按提示退出后重试，不使用 `sudo` 或关闭 SIP。

## Windows 账号目录与进程无法唯一对应

**当前普通模式开发修复包已按本人要求取消此账号占用对应门槛。** 读取只要求所选程序主进程唯一，实际密钥由全部所需库HMAC/完整性验证，并核对目录及本人昵称；不会因Restart Manager没有查到占用而拒绝读取。新会话不套用历史源/目标，可自行选择并按任意顺序核验。多个主进程、密钥失败或身份不明仍拒绝。下面内容仅用于旧版本/独立诊断，不再是新版读取的必经条件。

“无法唯一对应所选账号与微信进程”表示所选原版程序主进程与账号数据库占用进程的交集不是一个；仅看到微信已登录或目录中有数据库不能证明绑定成功。不要按目录顺序、修改时间或 PID 猜测账号，不放宽现有读取检查。

维护者可提供 `desktop/windows/diagnose-binding.cmd` 和 `diagnose_binding.py`，将二者放在便携包/安装目录的 `ChatRescue.exe` 旁边。仅在尚未进入应用的账号读取阶段，由本人保持本次原版微信登录，运行 CMD，输入准备页原版 EXE 路径和 `xwechat_files` 根目录。诊断只查询文件占用，分别输出 DB、WAL、SHM 的文件数量、占用 PID 及与主进程的交集；不打开数据库内容，不取钥，不启停微信，不修改账号或 ACL。输出不含完整账号名、昵称或路径，只保留目录序号与四位后缀。应用中断现场仍应保持微信退出，不能为运行此诊断启动微信。

诊断结果只用于区分主进程路径不匹配、DB 与 sidecar 占用差异、查询失败或多账号冲突，不能直接作为本人身份确认或实际取钥授权。没有匹配或多个目录匹配时继续停止，并保留结果排查。

2026-11-09 未发布源码修复：账号读取的占用检查增加已有 WAL/SHM，仍要求与所选程序主进程唯一匹配；只占用 sidecar 时不再因漏查误报无匹配。更换 B 目录或导入 B 密钥不再清除已经完成的 A 核验；更换 A 仍使双方失效。上述修复不证明某次现场失败必然由此引起。昵称标注“上次读取”表示历史设置，不是本次核验成功；零基础操作见 [读取步骤和常见卡点](windows-beginner-guide.md)。

## 密钥未捕获或 HMAC 失败

### Windows：缺少 media_0.db / 图片 DAT 缺少唯一可验证密钥

这两条截图错误来自不同前置条件。当前未发布开发修复包已经支持：

- 语音按实际存在的规范 `media_N.db` 枚举，只有非零分片也可核验；完全无语音库或音频本体时保留消息、跳过音频并计数，不要求创建 `media_0.db`。
- 图片源端解密参数不可验证、目标缺重加密样本时跳过该图本体，其他图片、视频、文件与文字继续；预览区分 `image_key_unavailable`、`image_target_unavailable` 和缺源文件等原因。数据库密钥不能代替图片密钥。
- 只有已确认不存在的媒体条件可以跳过；现有库的缺密钥/HMAC失败、身份/资源冲突、哈希变化仍停止。不要删库、删 WAL/SHM、修改旧回执或复制 B 密文绕过校验。

升级开发包后重新读取双方并生成新的具体预览，核对媒体恢复和跳过数量。旧媒体清单不含新能力，不能直接沿用。已发布的 0.5.6 下载行为不变；完整说明见 [媒体修复范围](windows-media.md)。

确认专用副本登录的是对应账号，`--db-root` 指向该账号当前使用的数据库，而不是旧账号、备份或另一个账号的库。正确的账号也可能因版本、结构或权限变化而失败；此时保留脱敏错误，停止导出和应用。

B 和 A 必须分别取钥。B 的密钥不能用于 A 的数据库。不要把密钥发到公开 Issue 让别人代为检查。

## 明文导出失败

先退出所有微信进程，核对数据库根目录、密钥文件和访问权限。导出使用 DB/WAL/SHM 的副本，不应手动删除源 WAL/SHM 来让命令通过。若 SQLCipher 完整性失败，停止后续 `save-chat` 和恢复；保留原库供重新导出核查。

## 首版范围拒绝

Windows 提示“消息收发方向与已核验版本不匹配”或“消息收发方向与所用方向配置不匹配”时，保留失败任务，核对完整版本与所属账号 `.capture.json` 回执；4.2.0.12 文本使用独立方向配置，不能通过修改 packed、owner 或消息编号绕过检查。更新后使用新任务重新导出并生成预览，不编辑旧导出报告或旧计划。Windows 的名片/文件方向仍未验证，遇到该类型停止，不删除消息来规避。

源码已支持现有编号分片，不应再出现“只支持 message_0.db”的旧版错误；出现该错误需更新源码/构建。所有分片必须有可验证密钥且结构兼容，不能漏掉分片。Mac/旧方向配置仍限文本 1、名片 42、文件消息 49 子类型 6；Windows 新结构配置允许所有正 int64 类型，但没有真实正 server_id、方向结构缺失或冲突时仍拒绝整段会话。不要删除分片、删除会话中的消息、编辑库或类型来绕过限制。附件内容本来就不恢复。

## 预览拒绝恢复

| 情况 | 处理 |
| --- | --- |
| 账号身份不匹配 | 重新核对 A/B 内部 wxid、当前登录账号与所选目录 |
| `server_id` 编号碰撞 | 逐条核对源与目标记录，不自动覆盖、不虚构编号 |
| 不支持的消息类型或数据库结构 | 停止恢复这部分资料，不把拒绝项说成已恢复 |
| 原库哈希变化 | 退出微信，使用新的输出目录重新生成计划并再次核对 |
| 候选哈希或完整性失败 | 保留报告，重新从可信 bundle 与原件生成计划，不编辑候选 |

## 应用失败

`apply` 在 `restore-plan/originals/` 保留原件，并在部分失败时尝试回撤。先检查 `applied.json` 或 `rollback.json`：后者 `state=rolled_back` 表示回撤成功，`state=rollback_failed` 与 `failed_paths` 表示仍有未恢复路径。只有 `apply-started.json` 而没有明确回执，可能是应用中断；不能重复运行同一计划。先核对原件及哪些文件已被替换。在未确认之前保持微信退出，不反复 `apply`，也不要直接启动微信。

全部消息分片、资源/会话库及其 DB/WAL/SHM 必须作为同一时刻的协调状态处理。不要从不同备份拼凑文件，也不要只恢复一个消息库。需要人工恢复时，先在报告中确认目标路径、原件位置与文件对应关系，保留失败现场的副本，再使用同次计划保留的整套原件恢复。若报告不能明确对应关系，停止操作，不猜测文件名或路径。

本版 CLI 没有独立的 `rollback` 命令。工具的部分失败自动回撤不等于应用成功后的任意撤销；人工恢复必须依据该次报告与备份核对。若此时已有新消息或手机迁移，不能简单把旧备份覆盖到现有库，应先保留当前资料再评估。

## 电脑或手机显示异常

电脑验收逐条检查身份、方向、时间与内容。出现异常时退出微信、保留计划和原件，停止进一步写入或手机迁移。

电脑可见但手机缺失，或方向不正确，不代表只需重新同步。历史实验表明消息编号与参与者元数据会影响手机端行为，但不能据此伪造真实消息编号。请按 [实测证据](evidence-and-support.md)理解边界，不把模拟实验结论直接泛化到真实恢复。

## 桌面启动提示原版微信仍在运行 / 退出码 255

A 副本保留原版应用标识，并使用相同账号目录。打开 Chat Rescue 前若原版仍在后台运行，A 可能立即退出；只关微信窗口不等于退出。切换到原版微信，用 ⌘Q 正常退出并完成可能的确认框，再回到登录页点击“打开微信 A”。不需要重新准备副本或删除任何聊天。

当前源码会在打开终端前及实际启动前检查冲突，并直接显示操作提示；允许固定的 A、B 副本同时运行，不自动结束原版进程。255 也可能有其他原因：原版已退出仍失败时保留当前错误详情和启动日志，继续定位，不据退出码单独判断权限或签名损坏。

## Windows 离线实验版故障入口

详见 [Windows 说明](windows.md)。缺少 DLL 时设置 SQLCIPHER_LIBRARY 为与 Python 架构一致的 SQLCipher 4 DLL 绝对路径，同目录准备其依赖；普通 SQLite DLL 不适用。ACL 检查失败时在 NTFS 本人私有目录用 init-work 创建新工作目录，不绕过检查。微信进程仍在时从菜单正常退出并检查托盘；进程查询失败会阻止写入。Mac 的 capture-keys 在 Windows 不可用，不能仅靠改平台标记运行。结构/密钥不兼容时停止，不删分片、不改消息类型。

Windows `capture-windows-keys` 是面向 4.2.x.x x64 的独立实验命令，此时指定微信需要已由本人登录运行。签名/版本/路径/PID/用户不匹配时停止；访问被拒绝不自动提权。未找到 Config.Cipher、HMAC 不通过或任一分片/辅助库完整性失败时不保存部分结果，不能改参数跳过验证；本机仅有两个 4.2.0.12 账号的成功取钥证据，不外推其他完整版本。取钥完成后本人退出微信，之后离线命令仍要求所有微信退出。

若计划前后的消息库/WAL 哈希相同而 SHM 改变，也必须保留现场并重新生成计划。SQLite 的只读核验可能更新 SHM reader 状态，这不授权修改旧计划或丢弃 sidecar；验证密钥安排在新计划前。

## 语音实验模式错误

0.4.0 本地开发版需在读取页勾选语音实验模式，CLI 对取钥/验证/导出/会话保存/计划生成加 `--include-voice`；普通模式仍拒绝类型34。缺媒体密钥时重新完成五库验证，不能四库成功即继续。仅支持默认 data_index、单行、已适配状态与方向；其他结构、额外媒体分片、缺音频或冲突应保留原件停止，不删记录或伪造编号。完整处理规则见[语音实验说明](voice-recovery.md)。

媒体加入后，中断处理和人工恢复也须核对 media_0.db 及其 DB/WAL/SHM；查 apply-journal.jsonl、apply-started.json 和各回执。缺少明确结果时保持微信退出，不重跑、不只恢复一个库。

## 图片、视频与文件实验模式

读取页开启附件实验开关，CLI导出/保存/计划加`--include-attachments`；含语音时另开语音。旧bundle缺附件清单需重新导出。源端只有缩略图、缺视频或文件时停止；双向可检查另一侧原件，双方缺失不能补出。DAT目标密钥必须有可核验样本，缺样本或未知布局时不能猜测、直接搬密文或把缩略图冒充原内容。

图片目录按目标单聊username映射；文件标题、长度和MD5必须一致。预览后附件被改动、出现新文件、候选篡改或路径符号链接都将拒绝应用。失败/中断处理须同时保留数据库及original-assets、文件候选、apply-journal.jsonl和回执，按[附件说明](attachment-recovery.md)处理，不只恢复消息库。

Windows 0.5.2 的程序检查和取钥回执接受完整 4.2.x.x，不再精确限制 4.2.0.12。导入已有 keys.json 时须在同目录保留其本人账号的 keys.capture.json；界面只记录密钥路径。缺少回执时仍按 legacy-v1 发送标记 1 处理，而已观察的 Windows 文本发送标记为 3，旧导出缺少配置也会触发方向冲突。这不能直接认定用户操作错误。回执完整仍失败时需核对实际方向兼容性；不修改回执、版本号、消息字段或旧计划。升级后保留原任务，重新导出并生成新预览。
