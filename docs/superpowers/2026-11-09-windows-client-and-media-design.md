# Windows 下一版：固定微信程序、读取流程与媒体兼容

日期：2026-11-09。状态：本人已确认按此设计实现，并追加“不支持图片/视频格式跳过本体并计数”要求。维护任务不启动微信、不取真实密钥、不写真实聊天库。

## 已明确的需求

- 用户选择随工具附带固定版本的完整微信程序，而非从使用者本机生成副本。
- SID 已有本地补丁，只需合入下一版，不另打 SID 专包。
- 处理读取昵称时偶发失败，改善 A/B 登录、目录发现与核验流程。
- 扩展语音、视频格式和多数据库支持；项目首页补清晰介绍与零基础操作入口。

## 固定完整微信程序

发布物增加独立的完整微信程序目录。来源必须是可追溯的腾讯原版分发，记录完整文件版本、架构、签名和逐文件 SHA256；保留原始文件，不修改签名、注入或自动提权。不使用只含 EXE 的不完整副本，不自动退回本机其他版本。

准备页显示所带微信完整版本与校验结果。启动和取钥绑定该目录的实际进程路径；启动前拒绝已有微信占用，A 核验退出后才能处理 B。用户仍亲自登录、手机确认、导入 B 记录和核对身份。

**固定程序目录不等于独立数据目录。** 本轮没有已验证的 Windows 微信便携/独立数据目录参数，也不能套用 Mac 重签方案。首轮按实际配置与 DB/WAL/SHM 占用确认数据位置；不得宣称运行副本自动得到空白账号环境。若要求完全不接触现有微信数据，须先另行验证可用的隔离运行方式，未验证前不提供“全隔离”入口。参考 [Microsoft 对打包、AppContainer 与数据虚拟化的区别](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)。

实施时已从腾讯官方安装包只解压取得4.2.0.13完整程序，主程序及核心DLL签名有效；详见 [离线副本记录](../windows-portable-client.md)。不能只凭官网“4.2”下载标题固定为某个四段版本，也不能将用户现有安装目录当干净发布输入。载荷准备、离线签名/完整性核验、本人登录与导入实机验收是三个独立阶段。

## 读取昵称和 A/B 流程

独立修复：进程占用检查覆盖消息库、辅助库和各自已有 DB/WAL/SHM；仍仅接受所选程序主进程的唯一交集。缺失或歧义拒绝，不按 PID、目录顺序或修改时间猜测。

更换 B 目录或密钥仅清除 B 核验；更换 A 则双方核验失效。双方授权确认、B 来源完整性确认和具体应用确认保持。历史昵称显式标为上次读取，本次成功只能来自经密钥验证的本人联系人唯一匹配，不能用缓存掩盖失败。

后续把读取错误区分为进程绑定、密钥/完整性与本人联系人三层；登录后刷新新账号目录，不把“没有昵称”和“没有账号目录”混为一谈。截图所示 A 未完成本次核验时，B 禁用符合顺序要求；不得为解决按钮灰色去掉该门槛。

## 媒体格式与多库

采用可扩展的按内容识别与校验，不仅凭扩展名。保留原始载荷；新增每种容器必须有明确布局、边界检查、合成正反例和清单兼容策略。格式识别、离线往返、微信内播放和手机迁移分别记录。不能把任意二进制以“兼容模式”写成可播放媒体。

现状：VoiceInfo 仅接受已适配的 SILK v3；视频候选主要按 MP4 路径及 ftyp 头处理；图片已有 PNG/JPEG/GIF/WebP、明确 BMP 布局、WXGF、HEIF/AVIF 容器识别及保守 DAT/XOR 转换。扩展前先确定真实语音/视频封装和消息元数据是否兼容，未取得格式依据的类型继续报告具体缺口，不能先宣布 AMR/MP3/AAC/MOV 等格式已支持。

多库按已有规范编号 `message_N.db` 与 `media_N.db` 枚举，逐片密钥、结构、独立身份映射、DB/WAL/SHM、候选、回撤和撤回必须覆盖。Windows 多消息片已有实现；多媒体片语音在未发布源码中已有实现。目标有多个媒体库时，只按 A 原有会话、真实消息编号和时间的唯一关联定位，缺失或冲突停止；没有可验证的新路由契约前，不按编号或样本时间范围分配，不自动建片。其他文件命名与数据库结构逐类适配，不无限放行。
