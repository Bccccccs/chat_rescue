# 实测证据与支持边界

## 2026-11-05 Windows 0.5.6 原生辅助表兼容

结构摘要确认，所选会话主表与资源辅助库符合现有要求；0.5.5 报错来自部分分片才创建 `MessageGroupTimeInfo`，以及 `SessionUnreadListTable_1`、`biz_info` 的字段物理顺序不同。这属于严格比较将已知原生差异误判为不兼容，不能归因于用户登录顺序错误，也不要求手动改库使字段顺序相同。

0.5.6 只对明确契约兼容：可选表出现时核对五字段和复合索引；两个已知只读辅助表按字段名称、类型、默认值、主键与逻辑索引比较。消息主表继续严格核验，A 原布局和辅助状态保留；未知字段、约束、索引、排序规则、外键或触发器仍拒绝。此处“结构一致”指恢复所需逻辑契约兼容，不要求 A/B 全库字节、联系人本地编号、分片数或物理列顺序完全相同。

该版本已发布，构建提交为 `6d747d5`；[双平台 CI 已通过](https://github.com/Bccccccs/chat_rescue/actions/runs/42042559384)，并完成合成故障回撤和包内运行时检查。媒体功能默认关闭，当前只有合成离线/加密证据，没有真实 Windows 媒体布局、客户端打开/播放或手机迁移验收。完整范围见 [发布说明](releases/v0.5.6.md) 和 [测试记录](testing.md#056-windows-发布验证2026-11-05)。以下历史记录按当时版本理解，不把早期实验结论外推为当前所有功能已验证。

## 2026-11-04 至 2026-11-05 恢复后历史月份不可见的排查

用户报告 0.5.4 应用后数量与报告一致，B 的 conversation.json 含早期记录，而 A 客户端上翻和日期选择均只能到较晚月份。后续历史审计确认：源合格消息、bundle、候选与当前 A 的真实编号集合和时间全部匹配，旧记录仍在 A 数据库，不能归因于漏导出或数量上限。可见性摘要显示源跨多个分片，A 全部集中在一片；原生 FtsRange 仍保留一个已无此会话表的旧分片范围。普通索引存在、排序无时间倒退，未观察到月份切点对应压缩格式变化。文件头 user_version/application_id 为零，不能据此推断分片顺序。这些证据指向原生分片/范围与候选分布不一致，但尚未完成新候选客户端验收。

0.5.5 在候选阶段用未改动会话交叉核对唯一分片时间标识、逐片身份及本地编号，再按时间分配所选会话；清理仅此会话的失效搜索覆盖，不伪造“已经索引完毕”。增加必需结构及候选索引比对，未知/歧义拒绝。合成用例覆盖分片文件编号顺序相反、缺证据拒绝、稀疏双向参与者编号、局部范围清理以及加密应用/撤回。此处不把已确认的数据库完整性写成真实微信显示或搜索重建已通过。

新增只读历史审计辅助工具：核对 B 快照、bundle、A 候选、应用文件哈希、逐月消息集合及时间变化；用户正常退出微信后，复用既有 A 密钥导出新的私有当前 A 快照，并在本机生成候选/当前 A 的单聊 JSON。仅汇总报告可分享，正文 JSON 与明文库留本机。2026-11-05 修正初版长时间无输出的问题：启动提示、十秒进度提示、progress.log 和分阶段原子保存的汇总报告；本机对话 JSON 改为单次扫描消息，不再执行恢复 bundle 的逐条资源查询，明确标注仅供诊断、不能恢复、资源省略，并保留系统消息。七项合成测试通过，包含总数相同但旧月份消息缺失、编号相同但时间变化、候选/导出篡改、失败仍保留报告、仅导出指定会话，以及完整快照/JSON 导出后 A/B 原文件哈希不变。已取得用户提供的汇总审计回执；本机开发未启动微信或再次应用真实库。

## 2026-11-04 Windows 文本方向待核验值 15

v2 后续回执确认：A/B 所有文本分组均为 field1=发送者本地编号，field2 在本分片 Name2Id 中对应接收者；field2 均不等于 real_sender_id。A 15250、B 39585 条文本中，self 消息的 field2 对应 peer，peer 消息对应 self。此证据支持在本账号对文本中按发送/接收双方身份映射两个字段，不能将 1/2/15/68 当固定方向标记。0.5.4 为此增加独立 participant-ids 配置及逐消息两端映射校验，保留不透明元数据、资源/会话、真实编号、冲突与原件保护。非文本同结构转换仍仅有合成验证；真实 GUI 应用、显示和手机迁移不因此视为验收。

后续脱敏汇总：A 文本 15250 条，B 文本 39585 条；字段 1 与分片发送者映射全部通过，未出现同编号配对的正文/发送者冲突。B 的 self/peer 均出现字段 2 为 1 或 2，self 另有 15；A 的 self 另有 68。同号、同正文及发送者的配对并非固定 3↔2。这否定了对此批资料把字段 2 直接当固定方向的适配前提；原少量 3/2 样本不能再外推。字段 2 是否为分片内本地编号仍需逐条映射检查，不能仅按数值相似性确认。诊断 v2 增加分片名、与 real_sender_id 是否相等及在 Name2Id 中对应的 self/peer 角色，不输出额外身份资料。

用户报告微信完整版本 4.2.0.13；0.5.3 现场错误显示 B 源文本类型 1、packed 字段 2 为 varint 15，按当前 structured 配置与发送者映射预期 3，候选被拒绝，未应用。此前报告的方向配置已确认为 Windows structured，不能将本次归因为缺失回执或系统消息。截图不证明 15 的完整语义或其他消息的布局，不据此添加 15→3 或按位截断的自动转换。

新增只读文本方向诊断工具，复用现有导出副本并核对清单哈希；按当前已选 A/B 账号目录绑定任务，用真实编号、发送者、正文和压缩内容在本机匹配两端，只输出方向/状态/来源数字和汇总计数。不读密钥、不打开真实库、不输出正文、编号、账号标识或路径，不修改报告或生成恢复候选。四项合成测试通过，包含 15/14 配对计数、错误身份/重复字段拒绝、导出篡改拒绝、正文不一致不作为证据及摘要不泄露原始资料；工具能在 0.5.3 内置运行时导入。合成 15/14 样例不属于实机配对证据，真实语义仍待诊断回执。

本地开发版0.5.0提供可选Mac原语音和图片、视频、文件附件实验模式，新增文件规则见[附件实验说明](attachment-recovery.md)和[语音说明](voice-recovery.md)。已发布0.3.7下载包不包含这些改动；实际打开/播放和手机迁移尚未验收。下面未注明媒体的步骤仍指基础模式。

## 证据分层

| 证据 | 已观察到的结果 | 不能据此宣称 |
| --- | --- | --- |
| 模拟文本、本地系统实验 | 电脑显示，`server_id=0` 时手机缺失；修改发送者映射后仍缺失 | 电脑可见即可保证手机恢复 |
| 模拟消息的非零实验编号 | 手机出现，但方向反了 | 可以为真实记录虚构编号 |
| 模拟消息补充对方 packed 短元数据 | 用户确认手机按对方侧显示 | 所有类型、所有版本都可迁移 |
| 真实跨账号两条消息：名片、文件消息条目 | 视角翻转后用户确认恢复成功，数据库字节比对通过 | 附件内容已补齐，或已完成完整手机跨账号实机验证 |
| 该真实案例的手机再次导出 | 没有独立截图或明确的逐项验收 | 已独立验证手机内容、方向与完整性 |

用户确认、数据库比对与独立手机分项验收属于不同证据。公开仓库不包含这些私人聊天、密钥或截图；也不包含伪造实验编号的工具。

## 首版范围

- 首版仅一个 `message_0.db` 消息分片；源码后续新增全部现有编号分片的恢复支持，证据见文末，不回溯修改首版实机结论。不得删除其他分片来绕过检查。
- 双方授权的单聊 bundle，从保留方 B 向误删方 A 恢复文本（类型 1）、名片（42）、文件消息（49 的子类型 6）条目。会话内出现其他类型时整段拒绝，不自动过滤跳过。
- 复制与重签专用取钥副本；保留原版微信。
- 密钥匹配、明文副本导出、参与者映射、恢复预览、去重、冲突拒绝和应用前校验。
- 本地三库候选与协调应用，保留原件，部分失败尝试回撤。

真实 `server_id` 必须来自源记录。手机号、微信号与真实账号身份不因视角改变；只调整本地映射和发送/接收方向。

## 不宣称覆盖的范围

群聊、附件内容补齐、撤回语义、所有特殊消息类型、其他平台与任意微信版本，不在首版覆盖承诺内。具体消息是否可恢复，以当前工具预览与校验结果为准。名片或文件消息条目恢复，不等于附件资源完整可打开。

项目不自动发送消息，不执行云端恢复，也不保证微信服务器或手机自动接受本地修改。电脑端验收与手机端手动迁移验收应分别进行；未验证的结果应标为未验证。

不要为恢复再次删除任何记录。群聊等不支持范围的说明不是要求用户删掉这些资料。

## 2026-11-04 多分片与 Windows 类型结构转换

源码新增现有编号消息分片的全链路清单：逐库身份解析、跨分片去重/碰撞拒绝、密钥覆盖、加密导出、候选及 DB/WAL/SHM 备份、应用中断回撤、双向补齐及完整撤回。使用临时合成账号与随机 SQLCipher 密钥验证，不是多分片真实账号恢复或客户端验收。不会自动创建新分片。
